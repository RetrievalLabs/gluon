# Test Extraction

## Overview

Test extraction captures integration, end-to-end, and acceptance tests as
first-class repository evidence.

Business extraction intentionally scans production Java sources only. That keeps
the production code model focused and avoids low-level unit-test noise, but it
also means integration behavior, externally visible workflows, fixtures, and
assertions are not represented directly. Test extraction fills that gap by
adding test-specific tables to the same `business-extraction.db`.

The extracted test model answers questions such as:

- Which integration or E2E test exercises this production method?
- Which API route or workflow is covered by tests?
- Which fixtures and assertions validate a business behavior?
- Which business knowledge graph facts can be traced to executable tests?

Unit tests are not included by default. They are usually closer to
implementation detail than business evidence and can introduce noisy links.

## Architecture

```text
Legacy Repository
       |
       +-- extract-business
       |      |
       |      v
       |  production code model
       |
       +-- extract-tests
              |
              v
          test evidence model

business-extraction.db
       |
       +-- modules / classes / methods / relationships / entry_points
       |
       +-- test_suites / test_cases / test_targets
       |   / test_assertions / test_fixtures / test_entry_points
       |
       v
Business KG builder
```

`extract-business` and `extract-tests` are separate CLI phases that write to
the same SQLite database.

`extract-business` owns the production code model. It writes production
`classes`, `methods`, `relationships`, `entry_points`, candidate scores,
evidence ranges, context packets, and diagnostics.

`extract-tests` owns only the `test_*` tables. It must not rewrite production
extraction tables. Re-running test extraction replaces the test extraction rows
transactionally so stale test facts do not remain after test code changes.

Keeping tests in the same database is intentional:

- Production method and class IDs are already stable database identifiers.
- Test targets can link directly to production `methods.id` and `classes.id`.
- The KG can trace business facts to both implementation evidence and test
  evidence without cross-database joins.
- The CLI does not need a second `--business-database` input.

## CLI Contract

```bash
code-parser extract-tests \
  --path <project-root> \
  --database <business-extraction.db>
```

`--path` points at the source repository.

`--database` points at an existing or writable `business-extraction.db`.
When production extraction has already been run, test extraction resolves test
targets to existing production methods and classes in the same database.

JDTLS is used for true target linking. Test method calls are resolved with
`textDocument/definition`, then mapped back to production `methods.id` or
`classes.id` by source file and line range:

```bash
code-parser extract-tests \
  --path <project-root> \
  --database <business-extraction.db> \
  --jdtls-command <command> \
  --jdtls-workspace <directory> \
  --jdtls-max-in-flight <count>
```

## Source Selection

Test extraction includes integration, E2E, and acceptance tests.

Included source patterns:

- Paths containing `integrationTest`, `integration-test`, or
  `integrationtests`
- Paths containing `acceptanceTest`, `acceptance-test`, or `acceptancetests`
- Paths containing `e2e`
- Files ending in `IT.java`, `ITCase.java`, `IntegrationTest.java`,
  `IntegrationTests.java`, `AcceptanceTest.java`, `AcceptanceTests.java`, or
  `E2ETest.java`

Excluded source patterns:

- Regular unit-test paths such as `src/test/java`
- Plain `*Test.java` files unless their path or filename clearly marks them as
  integration, E2E, or acceptance tests
- Generated and autogenerated sources
- Build outputs and VCS/tooling directories

Each included test source is classified with a coarse test kind:

- `integration`
- `e2e`
- `acceptance`
- `unknown_test`

The classifier should prefer explicit path and filename signals over framework
annotations. Framework annotations are additional evidence, not the only source
of truth.

## SQLite Model

Test extraction appends test-focused tables to `business-extraction.db`.

### `test_suites`

Represents a test class or suite-level container.

```sql
CREATE TABLE IF NOT EXISTS test_suites (
    id TEXT PRIMARY KEY,
    module_id TEXT,
    class_name TEXT NOT NULL,
    package_name TEXT,
    qualified_name TEXT NOT NULL,
    test_kind TEXT NOT NULL,
    file TEXT NOT NULL,
    start_line INTEGER NOT NULL,
    end_line INTEGER NOT NULL,
    annotations_json TEXT NOT NULL
);
```

### `test_cases`

Represents one executable test method or scenario.

```sql
CREATE TABLE IF NOT EXISTS test_cases (
    id TEXT PRIMARY KEY,
    suite_id TEXT NOT NULL,
    name TEXT NOT NULL,
    display_name TEXT,
    test_kind TEXT NOT NULL,
    file TEXT NOT NULL,
    start_line INTEGER NOT NULL,
    end_line INTEGER NOT NULL,
    annotations_json TEXT NOT NULL,
    body_text TEXT NOT NULL,
    FOREIGN KEY (suite_id) REFERENCES test_suites(id)
);
```

### `test_targets`

Links a test case to production code from the same database.

```sql
CREATE TABLE IF NOT EXISTS test_targets (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    test_case_id TEXT NOT NULL,
    target_kind TEXT NOT NULL,
    target_id TEXT NOT NULL,
    relationship TEXT NOT NULL,
    confidence REAL NOT NULL,
    source TEXT NOT NULL,
    FOREIGN KEY (test_case_id) REFERENCES test_cases(id)
);
```

`target_kind` should identify the target namespace, such as `method`, `class`,
or `entry_point`. `target_id` stores the corresponding production identifier,
for example `methods.id` or `classes.id`.

### `test_assertions`

Captures assertions and verification calls inside test cases.

```sql
CREATE TABLE IF NOT EXISTS test_assertions (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    test_case_id TEXT NOT NULL,
    assertion_kind TEXT NOT NULL,
    expression TEXT NOT NULL,
    expected_value TEXT,
    file TEXT NOT NULL,
    line INTEGER NOT NULL,
    FOREIGN KEY (test_case_id) REFERENCES test_cases(id)
);
```

Assertion kinds may include status-code checks, exception expectations,
boolean assertions, JSON/path assertions, body assertions, and verification
calls.

### `test_fixtures`

Captures setup, teardown, mocks, containers, embedded services, database state,
and external dependencies used by a suite or test case.

```sql
CREATE TABLE IF NOT EXISTS test_fixtures (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    suite_id TEXT,
    test_case_id TEXT,
    fixture_kind TEXT NOT NULL,
    name TEXT NOT NULL,
    details_json TEXT NOT NULL,
    file TEXT NOT NULL,
    line INTEGER NOT NULL,
    FOREIGN KEY (suite_id) REFERENCES test_suites(id),
    FOREIGN KEY (test_case_id) REFERENCES test_cases(id)
);
```

### `test_entry_points`

Captures externally visible behavior exercised by tests.

```sql
CREATE TABLE IF NOT EXISTS test_entry_points (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    test_case_id TEXT NOT NULL,
    kind TEXT NOT NULL,
    framework TEXT,
    route TEXT,
    http_method TEXT,
    topic TEXT,
    command TEXT,
    source TEXT NOT NULL,
    FOREIGN KEY (test_case_id) REFERENCES test_cases(id)
);
```

Entry points can represent HTTP calls, messaging topics, CLI commands,
scheduler triggers, or direct service API calls observed in tests.

## Traceability

Traceability is centered on stable IDs.

Production extraction stores production methods and classes in:

- `methods.id`
- `classes.id`
- `entry_points.id`

Test extraction stores links from tests to those identifiers in
`test_targets.target_id`. These links come from JDTLS definition locations, not
name matching.

The KG can use this relationship to explain test coverage for a business fact:

```text
business_nodes / business_edges
        |
        v
business_evidence.method_id
        |
        v
methods.id
        |
        v
test_targets.target_id
        |
        v
test_cases / test_assertions / test_fixtures
```

This keeps business knowledge traceable to both implementation source lines and
tests that execute the behavior.

## Failure Semantics

Test extraction should be transactional for `test_*` tables. A failed extraction
must not leave a partially refreshed test model.

Production extraction tables must not be modified by `extract-tests`.

Unresolved test targets should be written as diagnostics rather than blocking
test extraction. Integration and E2E tests often exercise code through
frameworks, HTTP clients, or generated proxies, so complete semantic resolution
is useful but not required for a usable test evidence model.

Missing or malformed individual test files should produce diagnostics while
allowing other test files to be extracted.

---

## Relationship To Business KG

The business KG should remain focused on business rules, workflows,
invariants, state transitions, side effects, and business concepts.

Test extraction does not add business KG nodes directly. Instead, it provides
evidence that the KG builder or later analysis tools can use to answer coverage
and validation questions:

- Which business rules have integration or E2E coverage?
- Which workflows are exercised through public API tests?
- Which assertions validate a state transition or invariant?
- Which fixtures are needed to reproduce a business behavior?

The KG can incorporate test evidence later without changing the production
code model or duplicating test metadata in `business-kg.db`.
